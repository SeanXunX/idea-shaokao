# Idea Shaokao — Interactive Review Dossier

## Intent and audience

The owner is a researcher deciding whether an idea deserves more time, implementation effort, or compute. This is a personal review artifact produced alongside a research report, not a marketing website. The central task is to make a defensible investment decision, then interrogate the reasoning behind it. The researcher should understand the proposed contribution, the SAC recommendation, the strongest unresolved risk, and the next decisive step without first reading the complete review archive. Deeper reading should reveal how a concern survived or changed through reviewer discussion and author rebuttal. Evidence must remain one action away, without losing the issue or the reader's position. The interface should feel deliberate, rigorous, and useful for sustained reading. It should also make unfavorable decisions legible rather than treating them as a failed product state.

The content itself supplies the visual motif: a claim passes through independent scrutiny, an author response, and chair assessment. Its supporting proof is more important than the final numerical score. A particularly valuable detail is the distinction between acknowledging a flaw and fixing the reviewed method. That relationship should become the organizing principle of the layouts. There are no decorative stock photographs, invented statistics, abstract network backgrounds, or imitation product screenshots. This document is the common input for three independent visual directions, all using the same actual test-case content and capabilities. The three real versions will be shown together before a final design is selected.

## Delivery and scope

Produce three self-contained English HTML files: signal-desk.html, editorial-dossier.html, and evidence-table.html. Target screenshot dimensions are exactly 1440×900, with a second verification viewport of 1024×768. Use responsive CSS; avoid document-level horizontal overflow. A direction may have its own layout and navigation model but must support the same flow: Overview → Critical issue → Evidence → Annotation → Export feedback. This phase is an interactive prototype. Skill runtime integration follows the user's visual selection. All CSS, JavaScript, content, and fonts are embedded by the build helper, with no runtime network requests or server requirement.

## Shared true content

The fixture is the earlier real one-round model-agent trial, explicitly labeled Test Case. Topic: Faster nonnegative projection. Proposed operator: P(x)=abs(x). Claim H01 says it solves min (z−x)² over z≥0 for every real x. At x=−1, the proposed output gives objective 4 while feasible zero gives 1. The exact projection is max(x,0). A separate quadratic example defeats unrestricted drop-in optimizer compatibility (H03). All three independent reviewers scored 1/10 initially and finally; these are actual scores, not illustrative numbers. AC and SAC both recommended Kill. The stage is Proposal, mode Independent model-agent review, one of one round completed, Not converged. External novelty and runtime are unassessed. E01 was an exact analytical correctness gate and failed. E02 timing and E03 optimizer benchmarking were conditional and canceled; there are no empirical runs. Confidence 5/5 concerns the algebra only. The author accepted the counterexamples and withdrew H01/H03 without changing frozen v01. The technical defects therefore remain Open in reviewed v01. Speed reporting alone is Resolved as an action/reporting requirement, without establishing speed.

Present four issue groups: correctness, optimizer compatibility, unknown novelty/significance, and speed reporting. Preserve all original reviewer issue IDs and group duplicate concerns transparently. Expose reviewer concern, author response, final reassessment, closure criterion, and evidence. Bundled sources contain exact original text and SHA-256 hashes. Narrative summaries may be concise but must remain faithful and link to source text. No invented citations, positive study outcomes, second rounds, or unperformed experiments are allowed.

## Visual directions and form

Signal Desk uses charcoal and warm white with a restrained ember signal. Its structural motif is a horizontal review sequence and an expandable issue/evidence inspector. Large controlled typography gives the verdict and core idea an unmistakable hierarchy. Editorial Dossier uses paper tones, serif headlines, precise rules, a reading column, and margin annotations. Its reference is Pentagram's MIT Technology Review editorial case study: https://www.pentagram.com/work/mit-technology-review. Transfer editorial clarity, not the publication's branding or wordmark. Evidence Table uses a light neutral palette, compact readable typography, an issue index, and aligned reviewer/rebuttal/reassessment columns. Its reference is Tufte's evidence-thinking principles: https://www.edwardtufte.com/notebook/analytical-design-and-human-factors/. Transfer comparison, provenance, and credibility, not a visual imitation. The three skeletons must differ structurally. Brand is the existing plain-text name idea-shaokao; no external product brands appear inside the prototype. Fonts are embedded open-license Manrope, Newsreader, and IBM Plex Mono. Body text is at least 14px, secondary labels at least 12px, and text contrast at least 4.5:1. Avoid purple gradients, decorative icons, generic colored-border cards, fabricated charts, and tiny text.

## Shared functional contract

Root agent supplies src/review-data.json, src/runtime.js, src/common.css, and an embedding builder. Designers own one src/<direction>.template.html. Include tokens /* EMBED_FONTS */ inside CSS and <!-- EMBED_RUNTIME --> immediately before a final initialization script. The builder replaces EMBED_RUNTIME with the JSON dataset and shared runtime. D is the dataset; UI is the runtime API. Call UI.mount('direction-slug') once after the token. UI.escape(value) safely encodes text. UI.issue(id) returns a data object. UI.issueBody(id) returns an inspector with the actual concern/response/reassessment, aliases, criteria, evidence, and annotation action. UI.sourceButton(id, optionalLabel) renders a source button. UI.noteButton(target, optionalLabel) renders an annotation button. UI.notesButton() and UI.exportButton() render common actions. Source buttons use data-evidence="source-id". Annotation buttons use data-annotate="target-id". Use data-show-notes and data-export-feedback for top-level actions. A data-issue="canonical-issue-id" click emits window event dossier:issue with detail.id; each designer owns selection and layout changes. Canonical issue IDs: R01-R1-01, R01-R1-02, R01-R1-03, R01-R2-03. Claim targets: H01, H02, H03. Section targets: decision, review-history, experiments. UI.showEvidence(id), UI.annotate(target), UI.showNotes() are also callable. UI.mount provides common accessible evidence/annotation/notes dialogs. Comments support Question, Needs evidence, and Suggested change; edit/delete, local drafts with honest fallback status, and Markdown export. Header buttons should include a visible note count via data-note-count and storage status via data-storage-status. All main navigation controls must perform real actions. Keep source evidence immutable and comments separate from scientific status.
